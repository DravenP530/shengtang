# 审核独立性：为什么执行者不能审自己

> 这是整套协议里最难、也最容易被跳过的一条。难不在技术，在**它反人性**——谁都愿意听「做完了」。

---

## 问题

多 Agent 系统里，最常见的失败不是「做不出来」，是**「做砸了但没人发现」**。

原因有三层：

1. **自我确认偏误**：执行者对自己的产出有滤镜，会挑对自己有利的标准
2. **角色重叠**：总控既分派又汇总，天然倾向于「报告好消息」
3. **上下文污染**：审核者如果看过执行过程，会不自觉地替执行者找理由——「他当时是这么想的，所以可以理解」

第 3 层最隐蔽。它不是道德问题，是**信息结构问题**：知道得越多，越难公正。

---

## 七条解法

### 1. 刑部本单不接活

**制度前提。** 一张升堂单里，刑部不承担任何执行任务。接了活，它就有了自己的利益，不再是第三方。

对应到升堂单的自检清单：「刑部**没有**被派执行任务」是必检项。

### 2. 验收标准前置

验收标准必须在**拆单时**就写死在升堂单上，不能事后补。

刑部只对照这张单子核，**不自己发明标准**。标准前置的意义是：执行者开工前就知道会被怎么量，不能事后调整尺子。

### 3. 顺序卡死

```
交活 → 刑部勘验 → 才进汇总
```

中堂**不能**跳过刑部直接汇总。这是硬约束，不是建议。

在界面上，这一条表现为「勘验中」是一个独立状态，中堂在勘验完成前无法进入「汇总中」。

### 4. 只认可复核证据

交活单必须有「证据」一行：文件路径、命令、输出、行号、链接。

**没有证据 = 未完成。** 不接受「已完成」「已处理」「应该没问题」。

「应该」两个字是审核的天敌。

### 5. 上下文隔离（最关键）

刑部只使用三样输入：

- 升堂单（验收标准）
- 交活单（交付物 + 结论）
- 证据（可复核的原始材料）

**不给它看执行过程。**

这条在 Agent 场景下的落地方式很具体：给刑部的 prompt 只贴这三样东西，**不贴**执行阶段的历史消息、不贴中堂和兵部的讨论、不贴失败重试记录。

看了过程，它就会替执行者找理由。这不是能力问题，是结构问题。

### 6. 降级要声明

如果这一单只有一个 Agent，没法分司，必须：

- 升堂单上写明「本单单司执行」
- 升堂结果上写明「**本单无独立审核，为主公自审**」

**假审核比没审核更糟**，因为它让人放松警惕。宁可明说自己审自己，也不要演一场假的三方核验。

### 7. 主公终裁

刑部只能「驳」，不能「否决」。

驳回必须写明：哪条不过、缺什么、补什么才算过。主公可以推翻刑部的驳回——但推翻要留痕（写一句为什么）。

**最终的独立性保障是人，不是流程。** 流程只负责把「不合格」这个事实摆到人面前，不替人做决定。

## 在界面里怎么演

| 阶段 | 画面 |
| --- | --- |
| 执行中 | 五司的灯全亮，**刑部的灯不亮**（它没接活） |
| 勘验中 | 五司全部压暗，**只留刑部在场** |
| 勘验 | 逐条打「核」；第 4 条因为只有结论没有证据被打 ✗ |
| 驳回 | 中堂：「第 4 条只有结论、没有证据。退回工部补交。」 |
| 补证 | 第 4 条变 ✓，其余不变 |

「执行时刑部不亮、勘验时其他司全暗」——这个视觉隐喻比任何文字说明都直接。

---

## 常见反驳

**「让刑部审，刑部自己也可能错。」**
会。所以有第 7 条：主公终裁。刑部的作用不是保证 100% 正确，是**把「有没有证据」这个最低门槛守住**。

**「每次都刑部审，太慢了。」**
慢的部分是「补证据」，不是「审核」。而补证据本来就是执行者该做的事——早补比晚补便宜。

**「一个 Agent 也要搞这套吗？」**
要，但要诚实。单 Agent 场景下，第 5 条（上下文隔离）没法真做，因为它是同一个上下文。这时候按第 6 条声明降级，不要假装。
