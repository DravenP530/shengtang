# 落地路线：从「演出」到「真干活」

> v0.2 是一台演出机。这一页讲怎么把它变成会干活的东西。

---

## 三条路线

| | A · 纯前端 | B · 自建后端 | **C · 寄生在 Agent Harness 上** |
| --- | --- | --- | --- |
| 做法 | 就是现在这版，脚本演出 | 自己写编排器 + 会话 + 工具 + 权限，前端推事件 | 演出层做成 harness 的界面插件，六司用它的子代理 |
| 好处 | 好看、零依赖、随手能演示 | 完全可控，学到最多 | 工具/权限/会话/子代理都现成，只写「朝堂」这一层 |
| 代价 | 不会干活 | 要造轮子，工程量巨大 | 要学插件体系；依赖上游预览版的稳定性 |
| 适合 | 作品集展示 | 想彻底搞懂原理 | **真想每天用** |

推荐：**A 保留做门面，C 做真实运行。**

## 为什么排除 Codex

Codex CLI 是 Rust + [ratatui](https://github.com/ratatui/ratatui) 的终端 TUI。

- 终端画不出惊堂木、卷轴、六席灯笼
- 要改界面 = fork 它的 `tui` crate 重写，成本极高
- 就算改出来，上限也就是「更好看的终端」

**结论：方向不对，不是难度问题。** 想要图形演出，就得自己掌控渲染层。

## 为什么选 DeepSeek Harness

以下是**已核实**的事实（截至 2026-10，以官方仓库为准，请自行复核最新状态）：

| 项 | 事实 |
| --- | --- |
| 仓库 | `github.com/deepseek-ai/deepseek-harness` |
| 许可 | MIT |
| 状态 | **Developer preview**（开发者预览版，`0.2.x-rc`），官方明示未经安全审计，Sandbox / Approval 不构成完全隔离 |
| 架构 | 基于 [Cordis](https://github.com/cordiverse/cordis)，**"Everything is a Plugin"** |
| 可替换范围 | 官方表述：模型适配器、工具、会话日志、**界面**和 Agent Loop 都可以通过插件树组合与替换 |
| 启动 | `npx @deepseek-ai/dsh web` → `127.0.0.1:3080` |
| 插件形态 | npm 包或 Git Bundle，`dsh plugin --profile web add <pkg>` |
| 模型接入 | Settings → Models 配 provider；支持自定义 OpenAI 兼容端点；可接 Ollama / 本地模型 |
| 多代理 | 支持子代理，且可为子代理单独指定模型 |

### 为什么这条路特别顺

1. **界面本身就是插件。** 我们不是去改它的代码，而是**加一个界面进去**。
2. **Agent Loop 也是插件。** 「升堂八态」理论上可以做成一个 Loop 插件，而不是外挂一层调度器。
3. **已经有人走通了「对话流里塞 HTML」**：`dsh-genui`（在回复里渲染图表/表单/3D 场景，并把操作事件送回模型）、`dsh-visualize`（在对话流里生成沙箱化交互 HTML 卡片）。我们的朝堂场景，本质就是一个大号的 genui 卡片。
4. **子代理 = 六司。** 天然对应，不用自己实现并发与隔离。

## 接入草案（v0.3）

```
┌─────────────────────────────────────────────┐
│  朝堂演出层（我们的 HTML）                    │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ 升堂单    │  │ 勘验单    │  │ 结果卷轴  │  │
│  └──────────┘  └──────────┘  └──────────┘  │
│         ▲ 事件流（SSE / WebSocket）          │
└─────────┼───────────────────────────────────┘
          │
┌─────────┴───────────────────────────────────┐
│  升堂 Loop 插件（TypeScript）                │
│  八态状态机 · 报文校验 · 闸门计数 · 附议轮    │
└─────────┬───────────────────────────────────┘
          │ 子代理调用
┌─────────┴───────────────────────────────────┐
│  DSH Runtime（工具 / 权限 / 会话 / 模型）     │
└─────────────────────────────────────────────┘
```

### 分四步走

1. **先只接编排层**：用 DSH 跑一个「拆单」任务，把输出喂给我们的界面渲染。验证模型能不能稳定输出升堂单格式。
2. **加报文校验**：升堂单必须能通过 schema 校验（每条任务有负责司、有交付物、刑部没被派活）。校验不过就让模型重出，最多 3 次。
3. **接子代理**：五司各起一个子代理，刑部单独起且**不给它执行上下文**（这是审核独立性的技术落点）。
4. **接事件流**：把状态迁移推给前端，演出层从「按剧本演」改成「按事件演」。

### 关键风险

- **格式漂移**：模型输出结构不稳定是最大障碍，必须做 schema 校验 + 重试
- **上下文膨胀**：六司并发 + 附议轮，token 涨得很快，闸门必须真生效
- **预览版不稳定**：DSH 是 rc，接口可能变，插件要锁版本
- **审核失效**：如果为了省事把执行上下文也塞给刑部，整套设计就白做了

## 一个必须先回答的问题

**模型够不够？** 分三层看：

| 层 | 要求 | 判断方式 |
| --- | --- | --- |
| 演出层 | 不需要模型 | 已完成 |
| **编排层** | 稳定输出结构化报文；连续 5 轮附议 + 2 轮改单不漂 | **必须实测**：同一需求连跑 10 次，看升堂单 schema 通过率 |
| 执行层 | 工具调用 + 长任务耐力 | 靠 harness，不用自己解决 |

编排层的门槛不在「聪不聪明」，在「稳不稳」。单次输出合格不算数，**连续十轮不跑偏**才是分水岭。

测法很简单：拿同一个需求，让模型连出 10 张升堂单，数有几张能通过 schema 校验、有几张会把刑部也派去干活。这个数字比任何 benchmark 都有用。
