# 升堂 · 把多智能体协作做成一场朝堂议事

> 输入需求 → 点「升堂」→ 惊堂木一响，六司齐呼 → 中堂拆单 → 附议 → 执行 → **刑部勘验** → 汇总 → 主公裁决

一个**可视化的多 Agent 协作协议**：把「谁在干什么、卡在哪一步、谁说了算」变成看得见的画面，而不是一屏滚动的日志。

![升堂单](assets/01-升堂单.png)

---

## 为什么做这个

多 Agent 系统真正的问题，不是模型不够聪明，是**过程不可见**：

- 用户不知道现在跑到第几步，只能干等
- 出了错，不知道是哪一环、该找谁
- 执行者自己汇报「已完成」，没人核
- 多个 Agent 各说各话，没有统一的报文格式，汇总时全是噪音

这套协议的解法和大多数框架相反：**不追求让 Agent 更自由，而是给它们定死一套朝堂礼仪**——固定的角色、固定的状态、固定的报文、固定的裁决方式。

礼仪不是为了好看。**礼仪是为了让过程可审计。**

## 六部制

| 位置 | 名号 | 职掌 |
| --- | --- | --- |
| 出题与裁决 | **主公** | 提需求、拍板、验收。只有你能「升堂」「定稿」「否决」 |
| 总控 | **中堂** | 唯一总控。拆单、派司、收附议、汇总。其他人不得直接找主公 |
| 一司 | **吏部** | 拆解需求、定人定责、写可勾选清单 |
| 二司 | **户部** | 资源、预算、素材、数据 |
| 三司 | **礼部** | 文案、呈现、对外表达 |
| 四司 | **兵部** | 攻坚、技术实现 |
| 五司 | **刑部** | **只审不做**：核证据、驳不合格 |
| 六司 | **工部** | 组装、打包、交付 |

选六部制不是为了复古，是因为**名字自带职责**。说「这活归兵部」，不用再解释兵部是干什么的——这比给 Agent 起名叫 `agent-3` 强得多。

## 八态状态机

```
待升堂 → 拆单中 → 附议中 → 执行中 → 勘验中 → 汇总中 → 待验收 → 结案
                    ↑                                      │
                    └──────────── 退回（写明改哪几条）──────┘
```

每一态在界面上只有一种合法画面，跳步就是错。

| 状态 | 谁在动 | 产出 |
| --- | --- | --- |
| 待升堂 | 主公 | 需求（含验收标准、禁区） |
| 拆单中 | 中堂 | 升堂单：目标、验收、约束、任务表、本单开哪几司 |
| 附议中 | 六司 | `附议` 或 `异议 + 改哪条 + 为什么`；最多 2 轮，吵不下上抛主公 |
| 执行中 | 各司 | 交活单：交付物 + 结论（三句内）+ 风险/未做 |
| **勘验中** | **刑部** | 勘验结论：逐条核证据，通过 / 驳回 |
| 汇总中 | 中堂 | 升堂结果：达成与否、交付清单、关键结论、待批事项 |
| 待验收 | 主公 | `定稿` / `退回` / `否决` |
| 结案 | — | 归档 |

## 三个关键设计

### 1. 附议轮必须能被打断

绝大多数多 Agent 流程是「派活 → 干活 → 汇总」，中间没有共识环节，错了只能返工。

这里加了**附议轮**：拆单后所有司必须表态，`附议` 或 `异议（写明改哪条、为什么）`。异议最多两轮，仍谈不拢就列分歧上抛主公拍板——**有兜底，不会死循环**。

原型里故意演了一次真实异议：兵部指出第 4 条工期不足，中堂当场把它拆成两期，二轮全附议。只演「全员附议」等于没演这个机制。

### 2. 刑部只审不做

这是整套设计里最难的一条：**执行者不能审核自己的工作**。

但在 Agent 团队里，中堂既分派又汇总，很容易变成「自己给自己打分」。解法是七条（详见 [docs/02-审核独立性.md](docs/02-审核独立性.md)），核心三条：

- **刑部本单不接活**——接了活就不是第三方
- **顺序卡死**：交活 → 刑部勘验 → 才进汇总，中堂不能跳过
- **上下文隔离**：刑部只看升堂单、交活单、证据，**不给它看执行过程**。看了过程它就会替执行者找理由，那是人情，不是审核

![刑部勘验](assets/02-刑部勘验.png)

界面上这一段是这么演的：执行阶段五司的灯全亮、刑部的灯不亮；勘验阶段五司全部压暗、只留刑部在场，逐条打「核」，第 4 条因为只有结论没有证据被打 ✗ 退回补交。

### 3. 闸门 + 按单设司，不设档位

**不设档位**。预设「轻量/标准/深度」三档是偷懒——活是千变万化的，先分类再干活必然错配。

改成**按单设司**：每张升堂单上直接写「本单开哪几司」。一司也能办，六司也行。看活配人，不做预设分类。

**闸门只留一条线**：单张升堂单一个 token 硬上限，到 70% 冻结范围（不许加活），到 100% 停工请主公裁决。不设「启动 15% / 调研 25% / 执行 40%」这种阶段比例——那是拍脑袋。

## 快速开始

无需安装、无需构建、无需联网。**双击 `prototype/index.html`** 即可。

在案几的奏折里写下需求，点朱红「升堂」印。

### 演示参数

| 参数 | 作用 |
| --- | --- |
| `?auto=1` | 自动填一段需求并开演 |
| `?auto=1&speed=4` | 四倍速，约 20 秒跑完全程 |
| `?pose=order` | 定妆：直接停在「升堂单」版式 |
| `?pose=verify` | 定妆：直接停在「刑部勘验」版式 |
| `?pose=result` | 定妆：直接停在「升堂结果」版式 |

界面右下角还有 `1× / 2× / 4×` 变速与「再升一单」。

## 设计取舍

**为什么是单文件、零依赖？**
演示一个想法不该要求别人先 `npm install`。一个 HTML 文件，双击就能看，发微信也能看。

**为什么音效是现场合成的？**
「惊堂木」那一声是整场戏的情绪最高点。但一个 wav 文件会破坏单文件约束，所以用 WebAudio 现场合成：噪声脉冲（木质）+ 低频正弦衰减（重量）+ 三角波余响（堂内回音）。

**为什么固定 1600×900 舞台而不是响应式？**
朝堂是有构图的画面，屏风、立柱、朝班、案几的相对位置都调过。流式布局在不同窗口下会散架，所以固定舞台 + 等比缩放，保证任何屏幕下构图一致。

**为什么不用动画库？**
演出是「节拍」不是「物理」。`async/await + wait()` 写出来就是一幕一幕的剧本，改节奏只改数字。CSS keyframes 管单个动作，JS 只管排幕。
